## Release decision

**Migration deployment remains blocked.** Do not run `supabase db push`, `db reset`, a replay, a baseline operation, a migration-ledger edit, or production DDL based on this inventory alone.

Safe recovery sequence:

1. Preserve a verified production schema, policies, functions, grants, extensions, triggers, storage configuration and role-privilege snapshot.
2. Recover the original SQL bodies for the remote-only versions from trusted Git history, backups or deployment records. Do not invent placeholder migrations.
3. Investigate duplicate timestamp groups and all nonstandard migration filenames. Each must be assigned an unambiguous, verified place in the migration history.
4. Reconcile local-only versions with the live schema to determine which are unapplied, superseded or represented by later migrations. Do not mark them applied just to make version lists match.
5. On a disposable Supabase/PostgreSQL environment, restore the authoritative migration chain and replay it from a clean baseline. Compare its resulting schema and security state with the production snapshot.
6. Only after independent review and positive/negative role tests, apply a controlled forward migration plan to production.

The November 30 public-launch candidate is not eligible for production deployment until this history has been reconciled and validated.
